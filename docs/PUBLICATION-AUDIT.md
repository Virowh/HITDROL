# Проверка перед публикацией HITDROL

Дата: 14 ноября 2026 года. Публичная версия — Beta 0.1, внутренняя сборка — 0.4.8.

## Результат

В обычном содержимом проверенного проекта личные данные Steam, Epic Games, GOG и SteamGridDB не обнаружены. Это результат проверки текущего снимка, а не гарантия для будущих сборок или добавленных файлов.

До подготовки публикационных материалов в проекте было 58 файлов, 7 695 869 байт. Проверены исходники Rust, тесты, PowerShell/Python-скрипты, оба Cargo.lock, документация, скрытые файлы, четыре PNG и WAV. В исходном снимке каталога Git и прежней истории коммитов не было; для публикации создан новый репозиторий с веткой `main`. Готовых MSI, EXE, ZIP, каталогов target, dist и artifacts в исходном снимке не было.

Искались файлы профиля и авторизации, SQLite-базы, логи, конфигурации окружения, приватные ключи, значения токенов и паролей, SteamID64, адреса электронной почты, личные пути, URL с учётными данными и длинные строки, похожие на ключи. Совпадения рассмотрены в контексте; одних названий переменных недостаточно, чтобы считать их секретами.

## Что найдено и как обработано

| Находка | Вывод и действие |
| --- | --- |
| OAuth-константы Epic/GOG в `src/accounts.rs` | Совпадают с опубликованными константами в [Legendary](https://github.com/derrod/legendary/blob/master/legendary/api/egs.py) и [Heroic gogdl](https://github.com/Heroic-Games-Launcher/heroic-gogdl/blob/main/gogdl/auth.py). Это данные OAuth-клиентов, а не личные access/refresh-токены или пароли пользователя. Сохранены. Это сравнение не подтверждает официальную поддержку HITDROL магазинами. |
| Строки `authorizationCode`, `access_token`, `refresh_token`, `api_key` | Обработчики авторизации, имена полей API, пустое состояние интерфейса и явно тестовые примеры. Сохранённых личных значений не обнаружено. |
| Длинные строки в Cargo.lock | Контрольные суммы зависимостей. Оба lock-файла сохранены. |
| Пути вроде `D:/Игры` и вымышленные идентификаторы | Тестовые данные. Пути с именем пользователя в обычном содержимом исходников не обнаружены. |
| Названия CPU/GPU в QA.md | Описание стенда измерений, без идентификатора устройства или аккаунта. Сохранено как контекст результатов QA. |
| Метаданные PNG | Логотип содержит IHDR/IDAT/IEND. Три слоя заставки дополнительно содержат C2PA: сведения о генераторе, времени создания, происхождении и подписях. Признаков личных аккаунтов в просмотренных метаданных не обнаружено. C2PA сохранены. Изображения просмотрены визуально, личных данных на них не обнаружено. |
| Метаданные WAV | Только `fmt ` и `data`; дополнительных текстовых разделов не найдено. |
| NTFS-потоки `Zone.Identifier` у 58 исходных файлов | В `ReferrerUrl` найден личный локальный путь к скачанному архиву. Сам путь в отчёте не повторяется. Это дополнительные потоки файловой системы; Git их не сохраняет. Исходные потоки не изменялись. Подготовленный ZIP исходников записывает только основной поток каждого файла и не включает эти данные. |

## Где остаются реальные пользовательские данные

По коду `src/storage.rs` локальная база создаётся в выбранном профиле; обычный профиль — `%LOCALAPPDATA%\HITDROLLauncher`. В нём могут быть библиотека игр, история, пути, настройки и личные изображения. Этот каталог находится вне проверяемого проекта и не включался в публикационный архив.

По коду `src/platform.rs` личный ключ SteamGridDB и refresh-токены Epic/GOG сохраняются через Windows Credential Manager. Содержимое хранилища учётных данных при этой проверке не читалось, не экспортировалось и не изменялось. Steam читает данные текущей локальной установки; файлов Steam-профиля в проекте не найдено.

В `.gitignore` дополнительно исключены локальные профили, распространённые файлы авторизации, `.env`, приватные ключи, SQLite и диагностические файлы. Это защита от случайного добавления новых файлов; она не удаляет уже опубликованные данные и не заменяет проверку перед выпуском.

## Материалы публикации

- `docs/DTF-POST.md` — текст поста со ссылкой на [Virowh/HITDROL](https://github.com/Virowh/HITDROL). Указано, что доступны исходники, а готовые пакеты приложения ещё не опубликованы.
- `dist/HITDROL-Beta-0.1-source-public.zip` — снимок исходников и подготовленных материалов, без NTFS-потоков и без сборочных/пользовательских каталогов. Это архив для разработки, не готовое приложение для игроков. Рядом записана SHA256.
- `artifacts/publication-audit-manifest.json` — локальный список упакованных файлов с размерами и SHA256; в ZIP не включён.

ZIP повторно открыт: список, размеры и SHA256 каждого извлечённого в память файла сверены с исходниками. Проверено отсутствие дополнительных записей, профилей, баз, логов, файлов авторизации и ссылок на локальный архив. Метаданные происхождения PNG сохранены побайтно.

Готовую программу необходимо отдельно собрать и проверить перед загрузкой в GitHub Releases. В этой среде `cargo` и `rustc` не обнаружены в PATH и стандартном пользовательском каталоге; сборка и Rust-тесты в рамках этой проверки не выполнялись. Число 87 тестов в QA.md относится к прежней проверке, а не к новому прогону.

## Размещение на DTF

Проверены [правила DTF](https://dtf.ru/rules) и описание темы [«Софт»](https://dtf.ru/software). Раздел 2 правил допускает ссылки на собственные проекты, пока публикация полезна сообществу и не используется в коммерческих целях; раздел 1 запрещает спам и агрессивное размещение внешних ссылок. Из этого следует, что ссылка на GitHub Releases бесплатного некоммерческого HITDROL уместна в содержательном авторском посте. Это вывод по правилам, а не отдельное разрешение модерации.

Перед размещением:

1. Репозиторий исходников: [Virowh/HITDROL](https://github.com/Virowh/HITDROL), ветка `main`. Оба Cargo.lock и LICENSE сохранены. Следующий шаг для распространения готового приложения — собрать, проверить и приложить MSI/ZIP к GitHub Release вместе с SHA256 и указанием внутренней сборки 0.4.8.
2. После выхода готовой сборки обновить раздел скачивания в посте ссылкой на конкретный релиз. Не выдавать ZIP исходников за готовую программу.
3. Добавить реальные скриншоты интерфейса и короткое видео на портативке: библиотека → карточка → запуск → возвращение → добавление сторонней игры. Эти материалы ещё не созданы; не заменять их обещаниями совместимости.
4. Проверить кадры на имена аккаунтов, уведомления, личные пути и коды входа. Для снимков приложения использовать отдельный демонстрационный профиль, описанный в README.md.
5. Опубликовать пост в «Софт». Гарантии рекомендаций или прохождения модерации нет.

На GitHub публикуется проверенный исходный снимок и материалы проекта. На DTF пост не размещался. EXE/MSI и релиз готового приложения не опубликованы. В код приложения изменения не вносились.
